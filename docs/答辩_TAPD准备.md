# TAPD 相关答辩准备

## 评委可能问的 TAPD 问题

| 问题 | 回答 |
|------|------|
| "你用 TAPD 管理了什么？" | 需求 Backlog、Sprint 任务看板、缺陷追踪三个模块 |
| "Backlog 有多少条目？" | 18 条需求，10 个 UC 用例 + 8 个增强需求，优先级 P0-P3 |
| "Sprint 怎么排的？" | 3 轮 Sprint，每轮 7 天，TAPD 看板 3 列：To Do / In Progress / Done |
| "缺陷怎么跟踪？" | TAPD 缺陷模块关联需求，21 条缺陷，P0(3)/P1(9)/P2(9)，18 已修复 |
| "怎么体现敏捷的？" | Daily Standup → TAPD 任务更新状态；Sprint Review → 验收测试用例；Retrospective → 缺陷统计改进 |
| "TAPD 和 GitHub 怎么配合？" | TAPD 管需求+任务+缺陷，GitHub 管代码+PR+版本；commit message 关联 TAPD 需求号 |

## 六、敏捷局限性（评委爱问）

> "作为 solo 项目，我们诚实地认识到敏捷的局限：
> 1. Pair Programming 和集体代码所有权难以落地——通过 PR + Code Review 弥补
> 2. 每日站会简化为个人进度记录——通过 TAPD 任务状态更新保持透明
> 3. 客户反馈循环较短——通过导师每周 Review 替代 Sprint Review 中的 stakeholder 反馈
> 敏捷不是教条，关键是迭代交付价值 + 持续改进的心态。"
