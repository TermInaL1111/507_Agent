# Scrum 敏捷开发 — 收获与心得

## 一、最大的收获

### 1. "Done" 的纪律比速度更重要

Vibecoding 让编码速度提升了 10x，但如果没有 Scrum 的"Definition of Done"，会陷入"写了一堆代码但没一个能演示"的困境。**每轮 Sprint 必须产出一个可演示的增量**——这个约束力是整个项目没有跑偏的核心原因。

> 心得：速度快 ≠ 产出多。Scrum 的 Sprint Review 强迫你停下来问"这轮到底交付了什么可用的东西？"

### 2. Backlog 优先级是救命稻草

20 天、97 个 commit、30 个工具——如果一开始就全部铺开，必然烂尾。**P0-P3 优先级**让每次 Sprint 只聚焦最核心的 5-10 个任务。

| 如果没做优先级 | 实际做的 |
|---------------|---------|
| 第一周做"收藏功能" | 第一周打通 Agent 对话 + RAG |
| 第二周做"UI 动画" | 第二周做课表/导航/培养方案 |
| 第三周做"帖子采集" | 第三周做 ReAct 可视化 + 冲突检测 |

> 心得：不是所有需求都值得做。P0 是"没有它系统不能用的"，P3 是"答辩加分但不影响主链路"。

### 3. Sprint Retrospective 让问题不被复读

每轮结束的回顾发现了很多"如果不回顾就会一直错下去"的问题：

| Sprint | 回顾发现的问题 | 下轮改进 |
|--------|--------------|---------|
| 1→2 | Agent 工具太少，回答空洞 | 新增 7 个工具 |
| 2→3 | 课表用正则 pre-check，绕过了 Agent | 删除 pre-check，直通 Agent |
| 3→4 | 工具调用只显示名字，看不出 Agent 在干嘛 | ReAct 可视化 |

> 心得：Retro 不是走过场——没有 Sprint 2 的 Retro，可能到答辩那天课表还在用正则匹配。

### 4. AI (Vibecoding) + Scrum = 超能力

传统 Scrum 里 PO 和 Developer 之间有沟通损耗。Vibecoding 消除了这个损耗——**PO 口述需求，AI 直接变成代码**。但 AI 不会主动说"这需求太大了，拆一下吧"——这是 Scrum 框架的职责。

> 心得：AI 是加速器，Scrum 是方向盘。没有方向盘的加速器只会更快撞墙。

## 二、Scrum 在三人团队中的实践

### 保留的（核心价值）

| Scrum 实践 | 为什么保留 |
|-----------|-----------|
| Sprint 固定周期 | 制造Deadline压力，避免无限拖延 |
| Backlog + 优先级 | 防止"想到什么做什么" |
| Sprint Review | 每轮必须有可演示产出 |
| Retrospective | 发现问题→下轮改进的闭环 |
| 任务拆分 | 大需求拆成半天能完成的小任务 |

### 简化的

| 简化项 | 原因 | 替代方案 |
|--------|------|----------|
| Story Points 估算 | 学生团队估算精度有限 | 按"半天/1天/2天"估工期 |
| Sprint Demo 会议 | 无外部客户 | 组内验收 + 导师 Review |

### 挑战与应对

| 挑战 | 应对 |
|------|------|
| 三人团队经验差异 | A (组长) 兼任 PO+SM，统一决策方向 |
| AI 辅助编程的代码一致性 | CLAUDE.md 约束 AI 行为 + PR Code Review |
| CI/CD 工具链学习成本 | C 专门负责，A/B 辅助，一次配置全组复用 |
| 课表解析等边界 case | TAPD 缺陷追踪 + Sprint Retro 集中复盘 |

## 三、举个具体例子

**Sprint 3 的"课表 pre-check 删除"决策**：

- **问题发现**（Retro）：课表查询走正则匹配，Agent 工具 `get_schedule_today` 从没被调用过
- **决策**（Planning）：下轮 Sprint 删除 `schedule_ai_service.py` 的 pre-check，让课表请求直通 Agent
- **执行**：删除 12 行正则代码，Agent 自动调用课表工具
- **验证**（Review）："我今天有什么课" → Agent 调 `get_schedule_today` → schedule_card 渲染 ✅

这是 Scrum 最经典的"发现问题→决策→执行→验证"闭环。如果没有 Sprint Retro，这个架构缺陷可能永远不会被发现。

## 四、核心心得总结

1. **Scrum 不是流程负担，是防撞护栏** — 速度快的时候最需要护栏
2. **Backlog 优先级是生产力** — "不做"比"做"更需要勇气
3. **Sprint Review 强迫交付** — 每轮必须有东西能演示，不能只"写了一堆代码"
4. **Retro 是唯一的学习机制** — 没有回顾就没有改进
5. **AI + Scrum = 超能力** — AI 加速执行，Scrum 保证方向
6. **小团队不是放弃 Scrum 的理由** — 核心实践（Sprint/Backlog/Review/Retro）依然有效，角色合并（PO+SM一人）降低沟通成本

## 五、答辩时怎么说（30 秒版本）

> 这次实习我最大的收获不是技术，而是**敏捷开发的思维方式**。
> 
> 20 天、4 轮 Sprint，我体会到了 Scrum 的三个核心价值：
> 
> 第一，**优先级取舍**——不是所有需求都值得做，P0 和 P3 的差距就是项目成败的差距。
> 
> 第二，**每轮必须交付**——Sprint Review 强迫你停下来问"这轮到底产出了什么可用的东西？"，而不是"我写了一堆代码"。
> 
> 第三，**Retro 是改进的唯一途径**——我们很多关键决策（删除课表 pre-check、引入 ReAct 可视化）
> 都来自 Sprint Retro 的反思，没有回顾就没有进步。
> 
> 同时，AI 辅助编程（Vibecoding）让开发效率提升了数倍，但 Scrum 的纪律确保了速度不变成混乱。
